# BBC SMS — Feature Completion Specification

Status: Proposed product and technical specification  
Date: 2026-08-05  
Repository: BBC SMS / Bayo Bilingual Complex school-management system  
Scope: Frontend, Spring Boot backend, PostgreSQL schema, parent portal, documents, security, reporting, and operational workflows

## 1. Purpose and baseline

This document turns the requested feature list into an implementable specification. It is based on:

- Direct review of the backend domain models, REST controllers, services, Flyway migrations, and Angular feature components.
- Live review of the application running at http://localhost:8082 using the supplied administrator credentials.
- Existing guide assets and UI templates in frontend/public/guide/img, including the student, attendance, bulletin, finance, and timetable screens.

The product is already a multi-tenant, bilingual French/English application with modules for students, staff, academics, attendance, finance, timetable, parent portal, health, discipline, documents, correspondence, alerts, and reports. The requested work is therefore a completion and hardening program, not a greenfield application.

### Current live baseline

The live administrator view currently shows:

- Students: 3 active students, family contact fields, photo support, imports/exports, and a post-registration parent-account panel.
- Presence: fingerprint-reader status, daily scan history, and status filters; no full class roster with an actionable mark state.
- Academic: class and sequence selectors, grade/bulletin/PV views, and sequence values 1–6.
- Journey: a student picker and manually entered year-by-year timeline.
- Finance: payments, debtors, expenses, fees, payment channels, and print-style receipts.
- Timetable: editable class weekly grid with teacher-overlap detection.
- Settings: sections, classes, subjects, holidays, roles, permissions, mail, and discipline catalogues; no academic-year management screen.
- Reports: financial summary, demographics, and a monthly attendance report.

### Current implementation gaps

| Requested capability | Current implementation | Required completion |
|---|---|---|
| Parent account during registration | Parent data is stored on the student; an account can be added later with username and password | Create or link a parent account inside registration, using email credentials and family linking |
| Full attendance roster | Daily board contains existing attendance rows only; unmarked students do not appear | Return the enrolled roster, allow present/absent/late/excused actions, bulk save, finalization, and analytics |
| Level-specific attendance | One record per student/date, suitable only for a daily roll call | Support daily primary attendance and secondary subject-period attendance |
| Profile photo on bulletin | Profile photo exists in the application but is not included in bulletin data/template | Embed the student photo in generated bulletins |
| Subject-specific remarks | Bulletin has a general appreciation and a locally derived generic appreciation | Persist teacher remarks per subject and show them beside the subject result |
| Academic sessions and promotion | academic_year table exists, but no administrative CRUD or promotion workflow | Add session management, class progression maps, review, bulk promotion, and history |
| Dynamic fee types | Fee configuration stores a JSON item list but the UI does not manage a fee-type catalogue | Add reusable fee types, class/session plans, exemptions, and student charges |
| Installments | Named tranches and due dates exist in a fee grid | Add charge-level allocation, partial payments, overdue status, refunds, and audit |
| Invoices, payroll, general ledger | Receipts are generated by the frontend print view; salary is a staff field; no payroll or ledger tables exist | Add official documents, payroll runs, double-entry posting, reconciliation, and reversals |
| Timetable conflicts | Backend checks teacher overlap, but an explicit allowOverlap flag can bypass it | Make conflict prevention strict by default, model legitimate shared groups explicitly, and add teacher views |

## 2. Product principles and shared foundations

### 2.1 Actors and permissions

The system must preserve least-privilege access and tenant isolation.

| Actor | Core responsibilities |
|---|---|
| Principal / administrator | Configure school, sessions, classes, progression, fees, roles, documents, and approve irreversible operations |
| Academic administrator / dean | Configure subjects, grading, attendance policy, bulletins, results, and promotions |
| Teacher | View assigned classes, mark attendance, enter marks and subject remarks, manage coursebook content, and view personal timetable |
| Form teacher / homeroom teacher | Manage the class roster, daily attendance, class-level academic review, parent correspondence, and promotion recommendations |
| Bursar / finance officer | Define charges, issue invoices, post payments, print receipts, manage payroll approval, and reconcile ledger |
| HR administrator | Manage staff records, contracts, leave, payroll inputs, and staff documents |
| Parent | Access only linked children, published bulletins, attendance, documents, fees, receipts, announcements, and messages |
| Auditor / reporting user | Read-only access to historical records, reports, exports, and audit events |

Every new endpoint must enforce both role permission and object scope. Teacher access must be restricted to assigned classes and subjects. Parent access must be restricted through the parent_student relationship, with no reliance on client-side filtering.

### 2.2 Academic session and calendar context

Academic session is a shared dependency for attendance, grades, fees, timetables, journey, documents, and promotion.

Required capabilities:

1. Create, edit, archive, and view sessions such as Session 2026-2027.
2. Store label, start date, end date, start year, status, and current flag.
3. Define terms or semesters inside a session, including labels, dates, sequence order, and publication state.
4. Enforce one current session per school at a time.
5. Prevent deletion of a session with financial, academic, attendance, or enrollment records; archive instead.
6. Configure teaching days, holidays, examination periods, school opening/closing times, and exceptional closures.
7. Require all new operational records to carry session_id and, where applicable, term_id.
8. Allow historical records to remain readable after a new session becomes current.

The current academic_year table and current-session lookup should be migrated into a managed domain rather than leaving the year as a free-text field or a bootstrap-only record.

### 2.3 Enrollment and historical class placement

The current student row contains a mutable class_id and class_name. This is insufficient for reliable year-end promotion and historical reports.

Add an enrollment or student_class_history record containing:

- student_id
- academic_session_id
- class_id
- enrollment status: active, withdrawn, transferred, graduated, suspended
- start date and end date
- entry type: new, promoted, repeated, transferred_in
- source promotion batch, when applicable
- audit fields

The current class on the student profile may remain as a cached convenience field, but historical reports and promotion must use session-specific enrollment records.

### 2.4 Audit, versioning, and approvals

The following changes require audit events with actor, timestamp, tenant, object, before value, after value, and reason:

- Parent creation, linking, unlinking, and credential reset.
- Attendance edits after finalization.
- Grade, remark, bulletin, and publication changes.
- Promotion preview, approval, commit, and reversal.
- Fee-plan changes, payments, refunds, invoice changes, payroll approval, and ledger postings.
- Timetable changes and any shared-group exception.

Validated bulletins, finalized attendance, posted financial documents, and committed promotions must be immutable in place. Corrections must create an amendment or reversal event.

### 2.5 Bilingual content and formatting

All catalogue labels, documents, notifications, and error messages must support French and English. A record may have a school default language and a user preference. Generated documents must use the selected language and the school identity from settings.

### 2.6 Document generation

Create one server-side document service for PDF/print generation. It must:

- Render from a versioned template.
- Embed school logo, student/staff photo, signatures, dates, and locale.
- Create a stable document number.
- Store or reproducibly regenerate the source data version.
- Return a printable PDF and a browser preview.
- Record who generated, downloaded, emailed, or reprinted a document.

Browser-only window.print() output is not sufficient for official invoices, receipts, bulletins, payslips, or promotion documents.

### 2.7 API and data rules

All new APIs must:

- Carry tenant scope through the authenticated context.
- Use UUIDs for relations and stable public numbers for documents.
- Validate dates, money, status transitions, and cross-tenant references on the server.
- Support pagination and filters for roster, payments, parents, and reports.
- Return structured errors with a stable code, user message, and field errors.
- Support idempotency keys for bulk saves, payments, payroll posting, and promotion commit.
- Use optimistic concurrency for editable aggregate screens.

## 3. Student and parent management

### 3.1 Objective

Register a student and establish a usable, secure family account in one workflow while allowing new siblings to reuse an existing parent profile.

### 3.2 Registration workflow

The New Student flow must have the following sections:

1. Student identity: matricule, NIU, names, sex, date/place of birth, photo, admission date, prior school, and repeating status.
2. Academic placement: session, section/subsystem, level, class, enrollment status, and start date.
3. Family and guardians: one or more parent/guardian contacts, relationship, legal name, phone, email, address, and primary-contact flag.
4. Portal access: create a new account, link an existing parent, or defer portal access.
5. Confirmation: show the student, selected class, parent account action, and duplicate warnings before save.

A registration save must be transactional. If a parent account or enrollment record fails, the student registration must not silently finish in a partial state.

### 3.3 Parent identity and credentials

Add a parent identity profile separate from the login record. It should support:

- Parent profile name, normalized email, normalized phone, address, relationship, and preferred language.
- One or more login accounts if the family policy allows it.
- A parent account linked to multiple children.
- Account status: invited, pending verification, active, suspended, disabled.
- Email login and optional legacy username compatibility during migration.
- Password hashing only; never store or return the plaintext password.
- Invite email, activation link, password reset, and credential regeneration.
- Login audit, last login, failed-login protection, and rate limiting.

The existing app_user table has username but no email. Add a tenant-scoped normalized email with a uniqueness policy, while explicitly deciding whether one email may be linked to more than one parent profile. The recommended policy is one parent identity per school/email and many children per identity.

### 3.4 Search Existing Parent

The registration form must provide Search Existing Parent.

Search behavior:

- Search by exact or prefix email, normalized phone, parent name, or existing username.
- Require at least three characters for name/phone searches.
- Return only authorized school-scoped matches.
- Show enough information to confirm identity without exposing unrelated family data: name, partially masked email/phone, number of linked children, and linked child names/classes after explicit selection.
- Require a confirmation step before linking.
- Warn if the selected parent is inactive, belongs to another school, or already has a conflicting relationship.
- Do not create a duplicate account when the user confirms a match.

Suggested APIs:

- GET /api/parents/search?q=&type=
- POST /api/students/{studentId}/parents with mode=create or link
- GET /api/parents/{parentId}/children
- PUT /api/parents/{parentId}
- POST /api/parents/{parentId}/invite
- POST /api/parents/{parentId}/reset-credentials

The existing post-registration parent link panel should use the same service and should no longer use a separate username-only flow.

### 3.5 Parent relationship and family rules

Support multiple parents/guardians for a student. Each link must store relationship, primary contact, receives academic notices, receives finance notices, receives discipline notices, and effective dates. Unlinking a child must not delete the family profile; it should only end the relationship and deactivate an account when no active child link remains, subject to audit retention.

### 3.6 Acceptance criteria

- Registering a student with a new parent email creates one parent identity, one account, and one parent_student link.
- Registering a sibling with Search Existing Parent adds a second link and leaves the original credentials unchanged.
- Duplicate email/phone matches produce a confirmation flow, not an automatic duplicate.
- A parent can log in and sees every linked active child, but no other student.
- Reset and invite links are single-use, expire, and do not reveal whether an email exists.
- CSV import can create a pending parent invite or link by email/phone, and reports unresolved duplicates.
- Staff can unlink or suspend access without deleting historical finance, attendance, academic, or audit data.

## 4. Attendance module

### 4.1 Objective

Provide a complete teacher roster workflow and reliable attendance analytics for both daily primary attendance and secondary subject-period attendance.

### 4.2 Attendance policy configuration

Create attendance policies at school, level, section, or class scope, with the most specific active policy taking precedence.

Required fields:

- Session and effective dates.
- Educational model: daily, subject_period.
- Required statuses and whether late counts as present.
- Start time and late threshold.
- Period definitions for secondary.
- Whether weekends, holidays, exams, and non-teaching days count in the denominator.
- Who may mark, edit, finalize, reopen, and approve.
- Whether device scans can create or update a record.

Default policies:

- Maternelle/Primary: one daily roll call per enrolled student and date.
- Secondary: one roll call per enrolled student, date, subject, and timetable period.

The current school-wide start time and one-record-per-day database constraint must be extended rather than reused unchanged.

### 4.3 Teacher roster view

The attendance screen must allow a teacher or form teacher to:

1. Select session, date, class, and, for secondary, subject and period.
2. Load the complete active enrollment roster, including students with no mark yet.
3. See photo/avatar, matricule, student name, current status, check-in time, source, late minutes, and note/reason.
4. Mark one student or bulk-select students as present, absent, late, excused, or medically excused.
5. Use a fast default action, such as Mark all present, followed by corrections.
6. Save the complete roster in one idempotent bulk operation.
7. Filter by status and search by name/matricule.
8. Finalize the roll call and see who remains unmarked.
9. Reopen only with the required permission and an audit reason.

Unmarked must be a distinct state until the roll call is finalized. The system must not infer that missing database rows mean present.

Suggested APIs:

- GET /api/attendance/roster?sessionId=&date=&classId=&subjectCode=&periodId=
- PUT /api/attendance/roll-calls/{id}
- POST /api/attendance/roll-calls/{id}/finalize
- POST /api/attendance/roll-calls/{id}/reopen
- GET /api/attendance/analytics?sessionId=&from=&to=&classId=&studentId=&subjectCode=

### 4.4 Data model

Replace the single daily uniqueness model with a roll_call and attendance_entry model:

- roll_call: session, date, class, model, subject, period, status, finalized_at, finalized_by.
- attendance_entry: roll_call, student, status, check-in time, late minutes, source, reason, note, created/updated by.
- attendance correction: original status, corrected status, reason, actor, timestamp.

A database uniqueness rule must prevent two entries for the same roll_call and student. Roll-call creation must snapshot the class membership for that date so later class changes do not rewrite history.

### 4.5 Device integration

Fingerprint/device ingestion must:

- Resolve student and session safely.
- Use idempotency keys.
- Map a scan to the active daily roll call in primary.
- Map a scan to a class/subject/period context in secondary, or explicitly record it as an arrival event without pretending it is a subject attendance mark.
- Preserve device time and server receive time.
- Reject scans for withdrawn/inactive students.
- Provide a reconciliation queue for unmatched or ambiguous scans.

### 4.6 Analytics

Analytics must be available by session, term/semester, date range, class, level, subject, student, and status:

- Present count.
- Late count and total late minutes.
- Absent count.
- Excused/medical count.
- Expected sessions.
- Attendance percentage = counted attended sessions divided by expected sessions, with the denominator policy visible.
- Unmarked and unresolved count.
- Class and level averages.
- Trend by week/month/term/session.
- Chronic absence threshold and alert configuration.

Expected sessions must be derived from active enrollment, calendar, roll-call policy, and finalized teaching sessions. A percentage based only on rows that happen to exist is not acceptable.

### 4.7 Acceptance criteria

- A teacher opening a class sees every enrolled student, even before any marks are saved.
- Primary can save exactly one daily roll call per student/date; a second save updates the existing entry.
- Secondary can record two different subjects in the same class/day and can record the same subject in different periods where configured.
- The backend rejects a duplicate roll-call entry under concurrent requests.
- A finalized roll call cannot be edited by a normal teacher.
- Analytics for a period include students with zero records and show whether missing sessions are unfinalized or absent.
- Parent portal attendance and reports use the same denominator and statuses as the staff module.

## 5. Academic records and report cards

### 5.1 Objective

Produce official, session-aware bulletins matching the school templates, with student photo and teacher-authored remarks for every subject.

### 5.2 Academic structure

Grades must be keyed by:

- session_id
- term_id or semester_id
- assessment/sequence identifier
- student_id
- subject_id or subject code

The existing sequence 1–6 values must be mapped to configured terms or assessment periods. A sequence without session and term context is not sufficient for historical reporting.

Grade entry must support mark, maximum mark, coefficient, grade status (submitted, absent, exempt, missing), teacher, submitted time, and correction history.

### 5.3 Subject-wise remarks

Each subject result must support:

- Teacher remark in French and/or English.
- Teacher identity and role.
- Optional standardized comment catalogue.
- Visibility/publication status.
- Character limit and safe text formatting.
- Amendment history after submission.

The remark is attached to the student-subject-period result, not to the student as a single general note. A general class-teacher appreciation remains a separate field.

Teacher UI requirements:

- Enter marks and remarks in the same class/subject grid.
- Bulk paste or keyboard navigation.
- Display missing marks and unsubmitted remarks.
- Show the assigned teacher for each subject.
- Prevent editing after publication unless the user has correction permission.

### 5.4 Bulletin content

Every generated bulletin must include, as applicable to the template:

- School name, logo, address, academic session, term, and document number.
- Student profile image with a safe placeholder when no photo exists.
- Student name, matricule, class, subsystem, date of birth, and attendance summary.
- Subject rows with subject label, mark, scale, coefficient, weighted result, and subject-specific remark.
- Total/average, rank, class size, class average, and grading interpretation.
- General appreciation and conduct/discipline summary where configured.
- Promotion or decision status where appropriate.
- Signature blocks for teacher, head of school, and parent, with signed/published status.
- Financial notice only according to a configurable school policy; it must not corrupt or hide the academic record.

Templates must support at least:

- Maternelle / competency-oriented template.
- Primary template aligned to the existing APC reference layout.
- Secondary numeric bulletin with coefficients, subject remarks, and term summary.

### 5.5 Workflow and publication

1. Teacher submits subject marks and remarks.
2. Form teacher reviews completeness.
3. Academic administrator validates the bulletin.
4. Principal publishes the session/term batch.
5. Parent portal exposes only the published version.
6. Corrections create a new version and optionally invalidate the old PDF.

Provide student, class, and batch preview before publication. Show blocking reasons such as missing subject marks, missing remarks, missing photo only when the school policy makes them mandatory, or unresolved attendance.

Suggested APIs:

- GET /api/academic/bulletins/{studentId}?sessionId=&termId=
- PUT /api/academic/results
- PUT /api/academic/remarks
- POST /api/academic/bulletins/{id}/validate
- POST /api/academic/bulletins/{id}/publish
- GET /api/academic/bulletins/{id}/pdf
- GET /api/academic/classes/{classId}/bulletins/export

### 5.6 Acceptance criteria

- A bulletin response and PDF contain the student photo URL or embedded image.
- Every configured subject appears, including a visible missing/absent state.
- The remark shown beside a subject is the persisted teacher remark, not a generic mark-to-text calculation.
- Two terms in two sessions never overwrite each other.
- A published bulletin is reproducible and remains unchanged when later grades are edited.
- Parent portal shows the published bulletin in the selected language and does not expose draft results.

## 6. Academic progression and student journey

### 6.1 Objective

Move students between sessions and classes in a controlled end-of-year workflow while preserving a complete academic journey.

### 6.2 Session management

Provide an administrator screen for:

- Session CRUD and archive.
- Terms/semesters and dates.
- Current session selection.
- Copying structure from a previous session: sections, classes, subjects, coefficients, policies, fee plans, and timetable period definitions.
- Locking a completed session.
- Validation that no two sessions overlap unless explicitly allowed.

### 6.3 Class hierarchy

Provide a progression map per subsystem and level. It must support labels used by the school, for example:

- SIL → CP → CE1 → CE2 → CM1 → CM2.
- 6ème → 5ème → 4ème → 3ème.
- Form 1 → Form 2 → Form 3 → Form 4 → Form 5.
- Terminale / Upper Sixth as terminal classes.

Do not hard-code these examples. The administrator must be able to:

- Create an ordered class path.
- Set the next class.
- Set terminal or graduation behavior.
- Set alternative paths for bilingual subsystems.
- Mark a class as non-promotional or repeatable.
- Define capacity and prerequisite warnings.
- Keep mappings versioned per session.

### 6.4 Promotion review workspace

The Promotion module must allow an administrator to choose source session, source class, and target session. It then shows one row per eligible student with:

- Student photo, name, matricule, current class.
- Average and rank.
- Attendance percentage, absences, and late count.
- Subject completion and failed subjects.
- Discipline summary.
- Fee balance warning.
- Current journey decision.
- Suggested target class from the progression map.
- Editable decision: promote, repeat, transfer out, graduate, exclude, pending.
- Destination class and note.

Eligibility rules must be configurable by level or school policy. Finance balance or attendance may be warnings, hard blocks, or no-block conditions; this must be explicit and visible rather than hidden in the transaction.

### 6.5 Bulk commit

The workflow must provide:

1. Preview and validation report.
2. Exportable decision sheet.
3. Admin approval with confirmation.
4. Transactional bulk commit with idempotency key.
5. Creation of next-session enrollment records.
6. Journey entry for each decision.
7. Cached current-class update only after successful commit.
8. Audit event and promotion batch number.
9. Downloadable promotion register.
10. Reversal or correction process that creates a compensating history event.

A failed student row must not cause silent partial promotion. The interface must show committed, rejected, and unresolved rows.

### 6.6 Acceptance criteria

- A session can be created and set current without deleting history.
- A class hierarchy can be configured without code changes.
- Promotion preview calculates a target class for each student and allows exceptions.
- Commit moves all selected students in one transaction and preserves their prior class placement.
- A repeated or graduated student does not receive an invalid next class.
- Two admins cannot commit the same batch twice.

## 7. Finance and accounting

### 7.1 Objective

Turn the current fee grid and payment screens into a complete, auditable school finance workflow connected to payroll and the general ledger.

### 7.2 Fee type catalogue

Create reusable fee types with:

- Code and bilingual name.
- Description.
- Default amount.
- Currency, currently FCFA.
- Tax or exemption treatment if required.
- Revenue account.
- Active/inactive status.
- Sort order and whether it is mandatory.

Examples: tuition, registration, examination, transport, meals, books, uniform, activity, insurance, and other configured school charges.

A fee type is not itself a student charge. It becomes a charge through a fee plan.

### 7.3 Class-level fee plans

A fee plan must be versioned by session and can target:

- School/level/subsystem default.
- Specific class override.
- Optional student-specific override.

Each plan contains fee-type lines with amount, quantity, discount, waiver, scholarship, due dates, and active dates. The system must explain precedence: student override, class plan, level plan, then school default.

Required controls:

- Draft, published, closed status.
- Effective session.
- Total computed from lines.
- Warning when a plan changes after invoices exist.
- Preview of affected students.
- No retroactive mutation of posted invoices.

### 7.4 Installments and payments

Installments must be first-class records, not only JSON:

- installment label and sequence.
- amount or percentage.
- due date.
- grace period.
- allocation priority.
- status: upcoming, due, overdue, paid, partial, waived.

Payment workflow:

- Select student, invoice/charge, installment, amount, method, reference, paid date, and payer.
- Validate active payment channel and required reference.
- Allocate payment to one or more invoice lines.
- Support partial payment, overpayment policy, refund, reversal, and unallocated credit.
- Generate a unique receipt number server-side.
- Never edit a posted payment; reverse it with a linked transaction.
- Send a notification to the parent if configured.

### 7.5 Invoice and receipt generation

Add official invoice records with:

- Invoice number, session, issue date, due date, student, payer, line items, subtotal, discount, total, balance, status.
- Draft, issued, partially paid, paid, overdue, cancelled, credited.
- Stable PDF/print output.
- School identity, tax/legal fields when required.

Add receipt records with:

- Receipt number, payment id, amount in words, payment method, reference, allocation, cashier, timestamp, and reprint history.
- A QR or verification code if the school wants public verification.

The current frontend-only receipt modal may remain as a convenience preview, but the official document must come from the backend.

### 7.6 Payroll

The staff record currently contains salary and hourly fields but there is no payroll transaction model. Add:

- Employment contract and salary history.
- Pay frequency and pay period.
- Earnings: base salary, hourly work, overtime, allowances, bonuses.
- Deductions: advances, absence, tax, pension, loan, other.
- Gross, total deductions, net.
- Approval state: draft, reviewed, approved, paid, reversed.
- Payment date, method, reference, and bank/mobile-money details as policy allows.
- Payslip number and bilingual PDF.
- Employee self-service access only to the employee’s own payslips.

Payroll must not calculate salary from a mutable current salary without preserving the salary effective at the pay period.

### 7.7 General ledger

Implement a minimal double-entry ledger:

- Chart of accounts with code, name, type, parent, and active state.
- Fiscal period with open/closed status.
- Journal entry header with source type, source id, date, description, status, and creator.
- Journal lines with account, debit, credit, cost centre, student/employee reference, and currency.
- Posting rules for invoices, student payments, refunds, expenses, payroll, and payroll payments.
- Reversal entries, not destructive edits.
- Trial balance, account ledger, income statement, receivables, payroll liability, and reconciliation report.

Examples:

- Issued tuition invoice: debit student receivable, credit tuition revenue.
- Student payment: debit cash/mobile-money clearing, credit student receivable.
- Approved expense: debit expense account, credit cash/payable.
- Payroll posting: debit salary expense, credit payroll payable.
- Payroll payment: debit payroll payable, credit bank/cash.

Posting must be idempotent. Every source transaction must show its linked journal entry and every journal entry must identify its source.

### 7.8 Acceptance criteria

- Admin creates a fee type once and reuses it across plans.
- A class-specific plan can contain multiple fee types and tranches.
- Changing a future plan does not rewrite issued invoices.
- A payment produces one official receipt and balanced ledger lines.
- A refund reverses the original allocation and ledger posting.
- A payroll run produces approved payslips and balanced journal entries.
- Trial balance remains balanced after fees, payments, expenses, payroll, and reversals.
- Finance exports can be reconciled by invoice, receipt, payment channel, and ledger account.

## 8. Timetable and scheduling

### 8.1 Objective

Support school-specific scheduling models, prevent invalid conflicts at the backend/database level, and give every teacher a personal timetable.

### 8.2 Scheduling configuration

Add session-aware schedule configuration:

- Week pattern and effective date.
- Days enabled.
- Periods with start/end times.
- Breaks and non-teaching periods.
- Rooms and room capacity/type.
- Class groups and combined classes.
- Teacher-subject and teacher-class assignments.
- Level model: homeroom or departmental.

The current fixed 07:30–15:30, nine-slot UI may be retained as a default but must be generated from configuration.

### 8.3 Nursery/Primary homeroom model

For Maternelle/Primary:

- Assign a homeroom teacher to a class for the session.
- Allow a teacher to cover all or most subjects for that class.
- Permit explicit specialist exceptions such as sports or language.
- Generate a teacher view from the class timetable and homeroom assignment.
- Warn when the same teacher is assigned to multiple homerooms at the same period.

### 8.4 Secondary departmental model

For Secondary:

- Assign subject-specific teachers to classes and subjects.
- Store workload and required weekly periods.
- Build timetable slots from subject assignments.
- Show unfilled subject periods and teacher workload.
- Support sets/groups where only part of a class attends a subject.
- Generate teacher schedule, class schedule, room schedule, and subject schedule.

### 8.5 Conflict prevention

The backend must reject, by default:

- A teacher in two classes at the same day and period.
- A room in two classes at the same day and period.
- A class in two subjects at the same day and period.
- A teacher assigned to an incompatible section or inactive contract.
- A subject period that exceeds the configured weekly requirement.

Validation must happen in the service and be protected against concurrent writes with a transaction plus database constraint or exclusion strategy. The current allowOverlap flag is too permissive for a strict policy.

If combined classes are a legitimate use case, model them explicitly:

- shared_group record with participating classes and teacher.
- an explicit reason and authorized creator.
- shared-group timetable slot rather than a hidden bypass.
- attendance and reporting behavior for the shared group.

There must be no generic “force save” path available to ordinary users.

### 8.6 Teacher-personalized view

Add:

- GET /api/timetable/teachers/{employeeId}?sessionId=
- GET /api/timetable/me
- GET /api/timetable/rooms/{roomId}

The teacher dashboard must show the current day, week, class, subject, room, start/end time, and conflict warnings. A teacher should not have to select classes one by one to reconstruct their schedule.

### 8.7 Print/export

Provide printable/PDF views for:

- Class timetable.
- Teacher timetable.
- Room timetable.
- Master timetable.
- Session/version and generated timestamp.

### 8.8 Acceptance criteria

- A concurrent attempt to book a teacher twice receives a deterministic conflict response and creates no second booking.
- Room and class conflicts are also blocked.
- A legitimate combined class requires a recorded shared-group configuration.
- Primary homeroom assignments produce a teacher schedule.
- Secondary departmental assignments produce a teacher schedule containing only that teacher’s slots.
- Changing the current session does not change historical schedules.

## 9. Additional missing or underdeveloped capabilities

These items were found while reviewing adjacent code and should be included in the product backlog because they affect the requested workflows.

### 9.1 Parent portal completion

The current parent API covers children, grades, class resources, fee statements, payment-channel instructions, and suggestions. Add:

- Published bulletin/PDF access.
- Detailed attendance history and absence reason.
- Notices, events, correspondence, and acknowledgement.
- Student documents with per-document visibility.
- Official invoices and receipts.
- Payment submission/status or payment-gateway result where the school enables online payment.
- Parent profile, language, notification preferences, and secure password change.
- Sibling switching with clear identity and class.
- Account invite and verification status.

### 9.2 Communications and notification delivery

Events and discipline notifications currently count recipients or simulate delivery. Add a notification outbox with:

- Email, SMS, WhatsApp, push, and in-app channels as configured.
- Provider configuration and templates in French/English.
- Delivery status, provider id, retry count, failure reason, and opt-out.
- Per-recipient consent and preferred channel.
- Batch throttling and provider rate limits.
- Parent acknowledgement and staff delivery audit.

SMTP test configuration exists, but actual business notifications must use a durable outbox rather than synchronous simulated delivery.

### 9.3 Staff, HR, and payroll prerequisites

Before payroll, add:

- Contract history and effective salary.
- Bank/payment details with restricted access.
- Leave, absence, and overtime approval.
- Staff documents and expiry alerts.
- Department and role history.
- Employee self-service for profile and payslips.

### 9.4 Health and safeguarding

The health module has student records, infirmary visits, and activities. Add:

- Consent and emergency-contact policy.
- Allergy, medication, immunization, disability, and accommodation records.
- Restricted health permissions and access audit.
- Incident severity, follow-up, closure, referral, and parent notification.
- Export of a controlled medical summary, never broad dashboard exposure.

### 9.5 Discipline

Add:

- Case lifecycle: open, investigating, actioned, closed, appealed.
- Evidence and attachments.
- Multiple actions and restorative follow-up.
- Configurable parent notification and acknowledgement.
- Separation between confidential staff notes and parent-visible summary.
- Session-aware reporting and appeal audit.

### 9.6 Documents and official records

The document area currently supports student files and orientation decisions. Add templates and lifecycle for:

- Enrollment certificate.
- Transfer certificate.
- Transcript.
- Bulletin and PV.
- Invoice and receipt.
- Payslip.
- Promotion register.
- Student ID card.

Include document number, version, signer, expiry, revocation, and download audit.

### 9.7 Reports and analytics

The current reports module is limited to finance totals, demographics, and monthly attendance. Add:

- Session/term filters on every report.
- Roster-based attendance denominators.
- Academic distribution, subject averages, pass/fail, rank, and trend.
- Promotion outcomes and repeaters.
- Fee plan, invoice, ageing, collection, waiver, and reconciliation reports.
- Payroll cost and headcount reports.
- Timetable workload and utilization.
- Parent-account coverage and unresolved family duplicates.
- Export to CSV/PDF with report parameters and generated-at metadata.

The displayed recovery-rate and balance figures must have one documented formula and the same data source as Finance; no dashboard should show a different result from the source module.

### 9.8 Class resources and coursebook

Classkit explicitly treats book prices as informational and does not post them to finance. Decide and document whether books/uniforms are:

- informational only, or
- chargeable items linked to fee plans/invoices and inventory.

The coursebook should link entries to session, timetable period, teacher, attachments, and parent visibility, and prevent edits to a historical locked day.

### 9.9 Data import and quality

Student and staff imports must:

- Validate all rows before commit.
- Show a preview with errors, duplicate matches, and warnings.
- Support parent email/phone linking.
- Preserve an import batch and source file hash.
- Allow safe retry without duplicating students, parents, invoices, or charges.
- Produce an error download.

Student soft deletion, class-name caches, free-text academic years, and legacy parent fields should be retained only for compatibility while the normalized records become authoritative.

### 9.10 Security and operations

Add or verify:

- Secure password reset and email verification for parents.
- Login throttling, session revocation, refresh-token rotation, and audit.
- Optional multi-factor authentication for administrators and finance users.
- File type, size, malware, and content checks for uploads.
- Database backup/restore test procedure.
- Health checks for PostgreSQL, email, notification providers, and attendance devices.
- Structured logs with tenant-safe identifiers and no passwords or sensitive medical data.
- Monitoring for failed ledger posts, notification backlog, device backlog, and document failures.

The repository currently has no backend or frontend automated tests visible under the inspected test paths. New work must include unit, integration, authorization, database, and end-to-end tests.

## 11. Acceptance and quality gates

A release is complete only when:

1. Every new workflow is tenant-scoped and authorization-tested.
2. Session and enrollment context is present in persisted records.
3. The UI has loading, empty, validation, conflict, permission, and retry states.
4. All official documents are server-generated, bilingual, printable, and auditable.
5. Financial actions are idempotent, reversible, and ledger-balanced.
6. Attendance and promotion operations are transactional and preserve history.
7. Parent accounts expose only linked children and only published information.
8. Migration scripts support an existing database without data loss.
9. API contracts are documented in OpenAPI and include example success/error responses.
10. Automated tests cover the acceptance criteria in this document.
11. A staging data migration and rollback/restore drill has been completed.
12. The product owner signs off the exact school policies for grading, attendance denominator, promotion eligibility, fees, payroll, and financial blocking.

## 12. Decisions required before implementation

The following policy choices must be confirmed by the school because they cannot be inferred safely from the existing code:

- Whether parent login is email-only, username-compatible, or both.
- Whether one email can represent multiple parent profiles.
- Whether excused and medical absences count in attendance percentages.
- Whether late counts as present for promotion and bulletins.
- Whether secondary device scans represent arrival only or each subject period.
- Whether a fee balance blocks bulletin publication or only displays a warning.
- Promotion thresholds by level, subject, and subsystem.
- Whether class capacity blocks or only warns during promotion.
- Whether books, uniforms, and activities post to finance.
- Required payroll taxes, deductions, approvals, and payment providers.
- Required accounting chart and fiscal-year rules.
- Approved SMS, WhatsApp, email, payment, and attendance-device providers.
